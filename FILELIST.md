# FILELIST.md

- `.gitignore` — Git ignore rules.
- `.gitattributes` — Marks binary assets (`.syso`, `.ico`, `.icns`, `.png`, `.zip`) so Git never applies line-ending conversion that would corrupt them.
- `go.mod` — Go module definition file.
- `.github/workflows/release.yml` — GitHub Actions: on a `v*` tag, runs `go vet` and `go test ./... -count=1` on Windows, macOS and Linux (CGO per leg, matching how each platform ships) and gates both build jobs on it, so a tag cannot publish a build whose tests fail; then builds the universal macOS `.app` (version injected) and the Windows `setup.exe` installer, publishes them to a GitHub Release, and bumps the multi-claude-switcher cask in `miou1107/homebrew-tap` to the new version + macOS zip SHA256 (needs the `HOMEBREW_TAP_TOKEN` secret).
- `.github/workflows/ci.yml` — GitHub Actions: runs the same three-platform `go vet` + `go test ./... -count=1` matrix as the release gate, but on every branch push and pull request instead of only on a tag, so a broken test surfaces when it lands rather than when someone tries to ship. Builds and publishes nothing.
- `go.sum` — Go module checksum file.
- `README.md` — User-facing overview: what it does, install, usage, troubleshooting (English). Says only what a user does and sees; how it works inside lives in `docs/`, this file list and the changelog.
- `README.zh-TW.md` — Traditional Chinese counterpart of the README: the same sections and facts, written in Chinese rather than translated sentence by sentence, with the button names the panel shows in Chinese.
- `FILELIST.md` — Inventory of project files and purpose.
- `CHANGELOG.md` — Project version and change history.
- `LICENSE` — MIT license text.

- `cmd/mcs-tray/main.go` — Go System Tray GUI entry point (cross-platform menu-bar / tray quick switcher). Hands `--open-claude-link` and `--unregister-claude-link` to `claudelink_windows.go` before its one-copy check, since both run beside the tray.
- `cmd/mcs-tray/claudelink_windows.go` — What runs when Windows hands the switcher a `claude://` link once the user has chosen it for them (issue #60): `mcs-tray.exe --open-claude-link "<link>"` refuses anything that is not a `claude://` link, ignores the link the panel opened to make Windows ask, and passes the rest to the Claude of the account the user is on (`core.ClaudeLinkTarget`). Logs the link only up to its query, which holds the sign-in code. `--unregister-claude-link` is the uninstaller's call that takes the switcher out of Windows' list of apps.
- `cmd/mcs-tray/claudelink_other.go` — Non-Windows stub: only Windows hands `claude://` links to the switcher.
- `cmd/mcs-tray/panellinks_windows.go` — The Windows panel's side of issue #60 and #61: renders the account list with the `claude://` notice and the Claude it drives at the foot, and runs the guide's button: asks Windows to show its app picker, keeps the panel up only while that window is open (`waitingForLinkPick`), returns to the list with what the user picked or stands down when the window closes without a pick, and takes the focus back afterwards so a click outside closes the panel again (parking it when it cannot). When Windows did not ask, the guide shows the Settings route and a late pick is still reported. A second press takes over from the first (`linkPickGen`).
- `cmd/mcs-tray/trayicon_darwin.go` — macOS tray icon (template PNG via SetTemplateIcon).
- `platform/protocolhandler_windows.go` — Points the `claude://` URL handler (`HKCU\Software\Classes\claude\shell\open\command`) at the profile Claude was launched on for as long as Claude runs on it (every profile except the default one), so a sign-in callback opens the profile the user switched to rather than the default one, and restores Claude Desktop's own registration once that Claude closes or the switcher exits. A restarted panel resumes or restores it (`ResumeProtocolHandlerHold` in `windows.go`). Re-reads the exe path on every write and rewrites the pristine form to restore, so a Claude update cannot leave a stale path behind. A path inside Program Files\WindowsApps, which the Store build registers and Windows refuses to start directly, is replaced with the Store alias (`launchableHandlerExe`). `protocolCommandFor` is the registry-free decision the once-a-second hold makes, tested so a handler it already wrote is never rewritten again.
- `platform/protocolhandler_windows_test.go` — Tests for the parsing and rendering behind that rewrite: exe extraction from quoted/unquoted forms, both rendered command shapes, reading a profile back out, a round trip proving repeated rewrites neither accumulate arguments nor lose the exe, which profiles get the handler held (a signed-in non-default profile included), which running profile a restarted panel resumes, and when a hold ends.
- `platform/claudelink.go` — The registry-free half of issue #60: with Claude from the Microsoft Store installed, Windows ignores the handler above and gives every `claude://` link to the Store app, which opens it on its default account. Decides from what Windows resolves `claude://` to and what the user picked whether sign-in needs the switcher chosen (`ClaudeLinkStatus`; Claude's own `HKCU\Software\Classes\claude` counts as fine, since that is the command the switcher holds on the account in use), lists the registry values that offer the switcher to Windows as an app for `claude://` (its name in Windows' window carries "recommended" in Windows' own language), defines the harmless link the panel opens to make Windows ask (`ClaudeLinkChooser`, `claude://hotkey`, which Claude does nothing with), and reads Claude's version from a Store package name, the claude.com installer's `app-<version>` folders, or a Mac Info.plist. Records why: Windows 10 refuses `SHOpenWithDialog` for a protocol and only asks while no app has been picked.
- `platform/claudelink_test.go` — Tests for the status decision (the Store app, the switcher chosen, the Store app or an unknown app picked, Claude's own handler picked, the claude.com build alone, the older Store build), the registry values, the "recommended" mark per display language, recognizing the chooser link as Windows hands it back, and the three version readers.
- `platform/claudelink_windows.go` — The Windows calls behind it: `AssocQueryStringW` and the user's `UrlAssociations\claude\UserChoice` for the status, registering and unregistering the switcher under HKCU (unregistering also removes the user's pick when it is the switcher, so Windows does not report a reset default), `AskWindowsForClaudeLinkApp` (removes an earlier pick of another app, then opens the chooser link and waits for Windows' OpenWith window), `ClaudeLinkChooserOpen` (whether that window is still up), `ClaudeLinkDisplayName` (the switcher's name as that window shows it), `RefreshClaudeLinkHandler` (the tray re-points an existing registration at itself on start), `OpenClaudeLink` (starts Claude on the account with the link; the default account gets no `--user-data-dir`, since the Store build keeps it elsewhere), and `ClaudeApp` for the panel's foot, which knows the Store package's family name even before Claude has first run.

- `internal/panelui/i18n.js` — The panel's localization, embedded in every page as a base64 `data:` script so a renderer check counting an English phrase in the HTML cannot also find it in the dictionary. Holds Traditional and Simplified Chinese: a dictionary of whole strings plus sentence patterns for the messages that quote a number or an account name. It reads `window.__mcsLang`, written by `i18n.go` from the stored setting, and falls back to the computer's own language when that says `auto`. Presentation only: it rewrites text nodes and `title`/`aria-label`/`placeholder`, and never touches form values, account names, action names, data attributes, the diagnostic report, or anything inside `translate="no"`. A `MutationObserver` covers the parts of a screen the host redraws in place.

- `internal/panelui/state.go` — `PanelState`: which screen is up, whether a row's rename editor is open, and whether a progress card is over the top, plus the rules for how the three interact (navigation clears the card, returning to the list via the non-navigation paths does not, the sticky notification is delivered under the lock). `Snapshot` reads all three together, so a host renders a screen and the card over it from one instant. - `internal/panelui/state_test.go` — Tests for `PanelState`, including a deterministic check that the sticky notification is delivered while the lock is still held, which is what stops one goroutine's notification overtaking another's.
- `internal/emdash/emdash_test.go` — Test-only package. Reads every string literal in `core`, `platform`, `cmd` and `internal` and fails on an em dash, exempting only log calls, so it covers copy no fixture happens to render (an error only produced when a particular call fails, a message box only shown when a runtime is missing) and copy that reaches a user without passing through a call at all. Skips `internal/panelui`, whose whole screens are single Go string literals and which has the stronger rendering guard instead. Replaced `core/emdash_test.go`, which checked `core` alone and so never saw the sixteen live em dashes in `platform/` and both hosts.
- `internal/hostparity/hostparity_test.go` — Test-only package. Reads both hosts' sources and fails when the macOS and Windows panel action switches stop offering the same set of actions, and renders every screen to fail when the page sends an action no host answers. The panel is one shared page, so an action handled by only one host is a button that silently does nothing on the other platform. It renders rather than scanning source because two Settings buttons build their handler by concatenation, which a source scan cannot see. It also renders every progress card, which no screen renderer produces, and fails when a card's Close or auto dismiss names an action no host answers, or when a card constructor is added to `internal/panelui` without being covered.
- `internal/panelui/progress.go` — The card the panel draws over whatever screen the user is on while a long operation runs, and for a moment after: a spinner while Claude is closed and reopened, a tick and what happened once it worked, or the failure and a Close button when it did not. `WithProgress` lays it over an already-rendered page, so every screen gets it from one call in each host rather than a view model threaded through each renderer. The walk is the hard part: an account name, a plan, an email address and the diagnostic report are the user's own data, and the script leaves them alone by asking the DOM (a `.chip` is skipped, a `.name` inside a row is skipped), which a pattern over the HTML cannot do — hence `golang.org/x/net/html`, held at the newest release whose own `go` directive still sits at or below this module's `go 1.22`. Four screens name copy the walk has to reach, so a walk that quietly stops early fails instead of reporting an empty page as clean.
